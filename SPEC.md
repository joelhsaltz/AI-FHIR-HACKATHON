# SPEC.md — Framework Requirements and Design Decisions

## Overview

This repository is a framework for generating self-contained Google Colab
notebooks that teach clinical informatics concepts through FHIR data querying.
Each notebook connects to a FHIR R4 server, presents a clinical scenario, and
guides students through structured activities that build understanding of how
clinical data is queried, interpreted, and acted upon — by humans and by AI
agents.

**Who this is for:** Clinical informatics instructors who want to teach FHIR
data querying and AI agent concepts using their own FHIR server and clinical
scenarios. The expected workflow is to fork this repository, configure your FHIR
server credentials, and either use the existing scenarios or create new ones for
your course.

**What it produces:** Self-contained Colab notebooks with all code hidden behind
form cells. Students interact through menus and dropdowns. No Python knowledge
is required. Each notebook is generated by a Python script — never hand-edited.

**Core assumptions:**
- A FHIR R4 server with synthetic or de-identified patient data
- An Anthropic API key (Claude) for AI agent activities
- Google Colab as the student delivery platform
- Students are clinically literate but not programmers

## Pedagogy Framework

### FHIR Is the Constant

Every scenario in this framework queries a FHIR server. The clinical question
changes, the activity structure changes, the pedagogical pattern changes — but
the underlying data layer is always FHIR resources retrieved through standard
queries. This is what makes the framework reusable: new scenarios reuse the
FHIR connection, tool definitions, and generator infrastructure while defining
their own clinical questions and educational activities.

### Educational Activities Vary by Use Case

The framework does not prescribe a single pedagogical pattern. Different
clinical questions call for different activity structures:

- **"You Are the Agent" (current):** Students manually perform an AI agent's
  job — choosing FHIR queries, interpreting results, making classifications —
  before watching a Claude agent do the same thing autonomously. Teaches agent
  loop intuition through direct experience.

- **Adverse event evaluation (planned):** Students review structured FHIR data
  (medications, conditions, observations) to assess whether an observed outcome
  is drug-related. Teaches evidence synthesis and causality reasoning.

- **Report integration (planned):** Students query FHIR resources from
  radiology and pathology reports, extract key findings, and integrate them
  with structured clinical data. Teaches cross-resource reasoning.

- **Population health queries (planned):** Students write natural-language
  requests that an AI agent operationalizes into FHIR queries across a full
  patient population. Teaches prompt design and agent-scale reasoning.

Each use case defines its own activity structure, UI pattern, and learning
objectives. The framework provides the shared infrastructure; the scenario
provides the educational design.

### Common Learning Goals

Across all use cases, students should develop:

1. Conceptual understanding of FHIR as a data standard — resources, queries,
   what you can and cannot ask for.
2. Ability to choose the next query given a partial patient record and a
   clinical question.
3. Understanding that single data points are rarely sufficient for clinical
   decisions.
4. Awareness of AI agent mechanics — tool calls, evidence gathering, reasoning
   chains.
5. Ability to evaluate whether an AI agent's clinical reasoning is well-supported.

Individual scenarios add scenario-specific learning goals (e.g., "explain why
kidney function complicates diabetes management").

### Target Audience Profile

Clinical informatics fellows and biomedical informatics graduate students.
The audience:
- Reasons fluently about diagnoses, lab values, medications, and clinical
  workflows
- Writes code roughly 5% of the time — comfortable with computers as users,
  not as programmers
- Should never be asked to write, read, or debug Python code during a session
- Includes both clinicians (MDs, nurses, pharmacists) who know the clinical
  domain deeply and PhD/MS students who may need clinical context provided

## Scenario Template Specification

Every clinical scenario is defined in a design document at `docs/scenarios/`.
The reference example is `docs/scenarios/diabetes-type-classification.md`.

### Required Elements

Each scenario design document must specify:

| Element | Description |
|---------|-------------|
| **Clinical question** | What the student is deciding — phrased as a question |
| **Classification categories** | The labels students assign (e.g., Routine / Moderate / High / No diabetes) |
| **Required evidence types** | Each FHIR resource type needed, with the specific code (LOINC, SNOMED) and a rationale for why it is needed |
| **Minimum queries to classify** | The number of queries needed to resolve any category correctly — must be >= 3 |
| **Phenotype-to-category mapping** | How each synthetic patient phenotype maps to a classification category, with teaching value noted |
| **Where ambiguity lives** | Which cases are genuinely hard and why — defensible disagreement, not trick questions |
| **Candidate pool strategy** | How patients are selected and presented (demographics only, no clinical data visible) |
| **Condition scrambling rules** | How to prevent the problem list from giving away the answer (if applicable) |
| **Clinical context card** | What clinical background must be provided so non-clinician students can engage |
| **Difficulty assessment** | Easy / Medium / Hard for the target audience, with time estimates |

### Quality Criteria (Six Tests)

Every scenario must pass these six evaluation tests. A scenario that fails any
test needs redesign before implementation:

1. **Single-Query Shortcut Test:** No single FHIR query resolves any
   classification category. If one lab value or one diagnosis code answers the
   question, the investigation phase is meaningless.

2. **Evidence Type Diversity:** The scenario requires at least 2-3 different
   FHIR resource types (e.g., Observations + MedicationRequests + Conditions).
   A scenario that only needs one resource type is too narrow.

3. **Ambiguity and Uncertainty:** At least two cases have genuinely defensible
   disagreement. If every case has a clear-cut answer, students learn lookup,
   not reasoning. Good scenarios include a mix of clear cases (confidence
   building) and ambiguous cases (evidence synthesis).

4. **Clinical Plausibility:** A real clinician would approach this problem the
   way the scenario asks students to. The task feels realistic, not
   artificially constructed for a classroom.

5. **Data Availability:** The FHIR server actually contains the data
   distinctions the scenario relies on. Verify against the live server, not
   assumptions.

6. **Difficulty Calibration:** The scenario matches the target learners'
   clinical sophistication, technical skills, and available time. Challenge
   their reasoning, not their domain knowledge or coding ability.

### Reference Format

New scenarios should follow the structure of
`docs/scenarios/diabetes-type-classification.md`, which includes all required
elements plus a self-evaluation section applying the six tests.

## Notebook Specification

### Delivery Format

- Self-contained Google Colab notebooks — no local `src/` imports
- All code cells use `cellView: "form"` metadata to hide Python from students
- Single pip install cell: `pip install anthropic`
- FHIR server credentials hardcoded (teaching server, not production)
- LLM API key retrieved from Colab Secrets
- FHIR query banners visible in output — the data retrieval process is part of
  the learning, not hidden infrastructure

### Common Cell Structure

All notebooks share this cell sequence at the top:

1. **Package installation** — `pip install` with output suppressed
2. **Setup and connection check** — imports, FHIR client initialization,
   connectivity test against the live server
3. **Tool definitions** — FHIR query functions with Claude tool schemas
4. **Validation cell** — quick query to confirm data access

After these shared cells, the notebook enters activity-specific cells that
vary by use case.

### Activity-Specific Structure

The cell structure after setup depends entirely on the educational design.
The "You Are the Agent" pattern uses:

- Clinical context card (background for non-clinician students)
- Candidate pool display (demographics only)
- Investigation loop (dropdown-driven FHIR queries with result display)
- Classification interface
- AI agent execution and comparison

Other patterns will have different structures. The framework does not
constrain what comes after the shared setup cells.

### Student and Instructor Versions

Each notebook has two versions:
- **Student version:** Activities only, no annotations
- **Instructor version:** Cell-level annotations explaining the pedagogical
  intent of each section

## Generator Script Specification

### Pattern

Notebooks are generated by Python scripts, never hand-edited. The generator
pattern (see `create_prototype_demo.py` as the reference implementation):

1. Define cell content as string constants at the top of the script
2. Use helper functions: `md_cell(source)`, `form_cell(source)`,
   `build_notebook(cells)`
3. Assemble cells into a list in presentation order
4. Write the notebook as JSON via `json.dump()`

This produces self-contained notebooks where all runtime code is inlined as
strings. The notebook has no dependency on the repository's `src/` directory.

### Why Strings

Generated notebooks must run in Google Colab without access to the local
repository. Inlining code as string constants ensures the notebook is
self-contained. The generator script is the source of truth — all edits happen
there, and the notebook is regenerated.

### Corresponding Smoke Test

Each generator should have a smoke test script that:
- Extracts code cells from the generated notebook
- Strips `#@param` annotations (Colab-specific syntax)
- Runs each cell in a shared namespace via `exec()`
- Mocks `input()` calls with test values
- Uses per-cell timeouts (longer for agent cells, shorter for others)
- Reports PASS/FAIL per cell with timing

The smoke test validates that cells execute without errors but does NOT
replace Colab verification (see Verification Requirements below).

## Technical Requirements

### FHIR Server

- **Protocol:** FHIR R4
- **Default server:** SBU LinuxForHealth at
  `https://lfh-fhir.eastus2.cloudapp.azure.com:9443/fhir-server/api/v4`
- **Auth:** HTTP Basic (`fhiruser` / `BmI512@ccess`)
- **TLS:** Self-signed certificate — all requests use `verify=False`
- **Dataset:** 1,027 synthetic patients across 6 clinical phenotypes
- **Configuration:** Server URL and credentials are configurable via `.env`
  for development. In generated notebooks, teaching server credentials are
  hardcoded to minimize student setup friction.

### LLM

- **Provider:** Anthropic only — no dual-provider abstraction
- **Model:** `claude-sonnet-4-20250514`
- **API:** `tool_use` (function calling)
- **Key management:** `ANTHROPIC_API_KEY` stored in Colab Secrets for
  notebooks, `.env` for local development

### FHIR Tool Schema Pattern

Agent tools follow the Anthropic `input_schema` format:

```python
{
    "name": "search_observations",
    "description": "Search for lab results...",
    "input_schema": {
        "type": "object",
        "properties": {
            "patient_id": {"type": "string", ...},
            "loinc_code": {"type": "string", ...},
        },
        "required": ["patient_id", "loinc_code"],
    },
}
```

The standard tool set covers: `get_patient`, `search_conditions`,
`search_observations`, `search_medications`, `search_encounters`. Scenarios
may add scenario-specific tools (e.g., `search_uacr` for kidney assessment).
All tools dispatch through a `_tool_runner` function that maps tool names to
FHIR query implementations.

## Design Decisions

### "You Are the Agent" replaces passive observation

The original hackathon format asked students to watch an agent run and then
experiment with prompts. Feedback indicated this was passive and disconnected
from clinical work. The "You Are the Agent" redesign puts students in the
agent role first. This is a design decision for the first use case, not a
constraint on the framework.

### Menu-driven interface hides Python

Students in this audience do not benefit from reading Python code. Human and
Hybrid modes present only clinical choices (labeled menu items) and data
returns (formatted as plain text). Underlying FHIR calls and API logic are
hidden in form cells.

### Anthropic-only LLM support

No dual-provider abstraction. Claude's tool_use API is idiomatic for this use
case and keeping a single provider avoids credential management complexity in
a classroom setting. The original codebase had 52 lines of setup + 130 lines
of agent loop for dual-provider support. Removing the abstraction simplified
significantly with no loss of functionality.

### Notebooks are generated, not hand-edited

Generator scripts are the source of truth. This ensures reproducibility,
makes changes auditable (diff the generator, not the JSON), and prevents
accidental edits to notebook JSON that break Colab compatibility.

### FHIR query banners are visible to students

Every query result displays a banner showing the FHIR URL that was called.
This makes the data retrieval process visible and is a core teaching point:
students should understand what FHIR queries look like, even if they never
write one.

### Scenario docs as shared artifacts

Scenario design documents (`docs/scenarios/*.md`) are the contract between
the scenario designer, the data architect, the notebook generator, and the
reviewers. All downstream work consumes the scenario doc. This prevents
drift between what was designed and what was implemented.

### Framework extraction from a single use case

The first use case (diabetes complexity assessment) was built as a prototype.
The framework was extracted from that prototype, not designed in the abstract.
This means the framework's abstractions have been tested against at least one
real scenario. Future use cases may reveal abstractions that need revision.

## Clinical Agent Pipeline

Four specialized agents support the notebook development workflow. Each agent
has a permanent identity file (`AGENT.md`) that is domain-independent, plus
per-project context from `project-brief.md`. Agents do not contain hardcoded
clinical codes or course-specific details — all domain knowledge comes from
the project brief and scenario design documents.

### Agent 1: Clinical Scenario Designer

**Trigger:** `/scenario-design`
**Identity:** `.claude/agents/clinical-scenario-designer/AGENT.md`

Designs clinical scenarios for any domain. Thinks simultaneously as a
clinician (what evidence matters), a dataset architect (what queries are
needed), and a teacher (is this non-trivial enough to learn from). Has access
to ICD-10, PubMed, and bioRxiv MCP tools for clinical grounding.

**Decides:** Clinical question, classification categories, required evidence
types, minimum query count, difficulty calibration, where ambiguity lives.
Applies the six evaluation tests to every scenario.

**Does NOT decide:** Code implementation, cell layout, UI patterns, data
generation parameters. Produces scenario design documents that others
implement.

**Escalates:** When data availability is uncertain (flags to Synthetic Data
Architect). When difficulty calibration is unclear for the target audience
(flags to Clinical Education Reviewer).

### Agent 2: Synthetic Data Architect

**Trigger:** `/synth-data`
**Identity:** `.claude/agents/synthetic-data-architect/AGENT.md`

Translates scenario designs into phenotype configurations for the synthetic
EHR generator. Maps clinical requirements (e.g., "low C-peptide in Type 1
diabetes") to generator parameters (anchors, distributions, bounds, coupling
constraints). Runs test batches and validates clinical plausibility.

**Decides:** Phenotype parameter values (anchors, spread, categorical
probabilities), cohort composition, coupling constraints between variables.
When the generator lacks needed variables, produces a variable extension
specification.

**Does NOT decide:** Clinical question design, classification categories,
pedagogical impact. Consumes scenario design documents as input.

**Escalates:** When a scenario requires variables the generator does not
support (produces a variable extension spec and flags for generator code
changes). When anchor values could be set multiple plausible ways (flags to
Scenario Designer for clinical guidance).

### Agent 3: Clinical Education Reviewer

**Trigger:** `/edu-review`
**Identity:** `.claude/agents/clinical-education-reviewer/AGENT.md`

Evaluates whether a notebook delivers on its learning objectives. Thinks as
an instructor (what should students learn) and a student advocate (would I
actually learn anything from this). Applies the "Bored or Baffled" framework
to every cell and activity.

**Decides:** Whether learning quality is sufficient, whether activities
provide real agency, whether difficulty is calibrated correctly, whether
feedback is immediate and specific. Produces a structured review with
severity ratings (blocks-learning / reduces-engagement / cosmetic).

**Does NOT decide:** Clinical thresholds, code implementation, technical
correctness. Evaluates pedagogy, not code.

**Escalates:** When clinical content accuracy is uncertain (flags to Scenario
Designer). When technical implementation issues affect the student experience
(flags to Notebook Implementation Reviewer).

### Agent 4: Notebook Implementation Reviewer

**Trigger:** `/nb-preflight`
**Identity:** `.claude/agents/notebook-implementation-reviewer/AGENT.md`

Catches technical issues that would otherwise require browser-based debugging.
Reviews 10 check categories: form/widget syntax, string escaping, cell
dependencies, Run All compatibility, package installation, secrets handling,
data query patterns, output/display, code visibility, generator consistency.
Also performs a clinical coherence check against the scenario design document.

**Decides:** Technical correctness, Colab platform compatibility, whether the
notebook matches the scenario design's intent.

**Does NOT decide:** Pedagogical quality, clinical scenario design, data
generation parameters. Flags technical and coherence issues; others decide
how to fix them.

**Escalates:** When a technical constraint conflicts with the pedagogical
design (flags to Education Reviewer). When clinical coherence issues suggest
the scenario design itself needs revision (flags to Scenario Designer).

### Inter-Agent Communication

- **Scenario design documents** (`docs/scenarios/*.md`) are the primary shared
  artifact. The Scenario Designer produces them; all other agents consume them.
- **Query files** (`agent-history/comms/queries/`) for decisions that cross
  agent boundaries. An agent writes a query file when it encounters a decision
  outside its domain.
- **Response files** (`agent-history/comms/responses/`) for answered queries.
- **Session files** (`agent-history/sessions/`) for cross-conversation context.
- **Decision boundary rule:** Agents flag decisions outside their domain rather
  than making them. The cost of a false alarm is one query file. The cost of a
  wrong assumption is a broken teaching experience.

### End-to-End Workflow

Creating a new scenario from idea to shipped notebook:

1. **Design:** `/scenario-design` produces `docs/scenarios/<name>.md`
2. **Data:** `/synth-data` consumes the scenario doc, produces phenotype configs
   and generated patient data
3. **Generate:** A generator script consumes the scenario doc and data,
   produces a Colab notebook
4. **Review:** `/nb-preflight` checks technical correctness and clinical
   coherence; `/edu-review` evaluates pedagogical quality
5. **Verify:** Notebook is tested in Google Colab with live FHIR data
6. **Ship:** Instructor reviews, merges, and distributes

## Verification Requirements

### Two-Stage Verification

1. **Automated (Claude's responsibility):** Programmatic cell execution against
   the live FHIR server. Currently uses Vertex AI Workbench with SSH tunnel and
   Jupyter MCP for structured output capture. Evaluates technical correctness,
   FHIR connectivity, cell execution, and output formatting.

2. **Manual (Instructor's responsibility):** Three items require Colab's
   rendering engine: dropdown widget appearance, dashboard HTML/CSS rendering,
   and code visibility (form cell behavior). The instructor reviews these after
   automated testing passes.

### What Counts as Verified

- Local smoke test passes (necessary but not sufficient)
- Automated execution against live FHIR data shows all cells succeed
- Change-specific checklist: every UI change is confirmed in at least one
  verification output
- Instructor manual review confirms the student experience

### What Does NOT Count

- "The code looks correct" or "this should work"
- Local Jupyter execution (Colab has different behavior)
- Testing against a mock or local FHIR server
- Verifying only the generator without running the generated notebook

See `TECHNICAL.md` for the full verification infrastructure (Vertex AI
Workbench setup, Playwright legacy tools, debugging guide).

## Known Constraints

- **Self-signed TLS certificate** on the default FHIR server requires
  `verify=False` in all requests. Students should be told this is a teaching
  environment, not production practice.

- **Synthetic data sparsity:** Synthea-generated patients may have sparse lab
  histories. Scenarios must handle missing observations gracefully rather than
  erroring.

- **Colab session timeouts** can interrupt long-running population queries.
  Notebooks with agent loops should include step caps and progress indicators.

- **Vertex AI cannot render Colab widgets:** `#@param` dropdowns do not render
  in Jupyter. Three verification items (widget appearance, dashboard rendering,
  code visibility) require manual Colab review.

- **Ambulatory-heavy encounters:** Inpatient metadata in the synthetic dataset
  is sparse. Do not design scenarios that depend on admission/discharge patterns.

- **No clinical notes:** Only structured data (codes, values, dates). Free-text
  reasoning is not available in the FHIR server.

- **Static dataset:** 1,027 patients, not growing. Query results are
  deterministic for a given query. New scenarios requiring different patient
  populations need synthetic data generation.

- **Limited condition vocabulary:** Only diabetes and CKD conditions are
  reliably seeded in the current dataset. Other conditions may be synthetic
  generator artifacts. New clinical domains require new phenotype generation.
