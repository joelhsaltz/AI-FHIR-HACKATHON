## Project

Framework for generating self-contained Google Colab notebooks that teach
clinical informatics through FHIR data querying. Each notebook connects to a
FHIR R4 server, presents a clinical scenario, and guides students through
structured activities. All code is hidden behind Colab form cells — students
interact through menus and dropdowns, never Python.

**FHIR is the constant.** The clinical question, activity structure, and
pedagogical pattern change across use cases, but the underlying data layer is
always FHIR resources retrieved through standard queries. The first use case is
"You Are the Agent" (diabetes management complexity assessment). Planned use
cases include adverse event evaluation, radiology/pathology report integration,
and population health queries.

**Current status:** Phase 0 prototype built and verified on Vertex AI Workbench
with live FHIR data. Four scenario designs complete. Open design issues:
combined dropdown UI, need richer multi-query scenarios.

## How to Add a New Scenario

End-to-end workflow from idea to shipped notebook:

1. **Design the scenario:** `/scenario-design` produces `docs/scenarios/<name>.md`.
   Must pass all six quality tests (see SPEC.md). Reference example:
   `docs/scenarios/diabetes-type-classification.md`.

2. **Generate synthetic data** (if needed): `/synth-data` consumes the scenario
   doc and produces phenotype configs at `synthetic-ehr/assets/`. Pipeline:
   validate config, generate cohort, validate output, export FHIR bundles.

3. **Write a generator script:** `create_<name>_notebook.py` following the
   generator pattern (see below). Copy shared cell groups from
   `create_prototype_demo.py`, add activity-specific cells.

4. **Write a smoke test:** `test_<name>_notebook.py` following the smoke test
   pattern. Extract cells, strip `#@param`, `exec()` in shared namespace with
   mocked inputs and per-cell timeouts.

5. **Review:** `/nb-preflight` for technical correctness + clinical coherence,
   then `/edu-review` for pedagogical quality. Run BEFORE Colab verification.

6. **Verify:** Vertex AI Workbench execution against live FHIR data, then
   instructor manual review in Colab (see Verification section below).

7. **Ship:** Branch (`codex/<topic>`), PR via `gh pr create`, update CLAUDE.md
   key commands/files, update CHANGELOG.md.

## Generator Pattern

Notebooks are generated by Python scripts, never hand-edited. See
[TECHNICAL.md](TECHNICAL.md#generator-pattern) for the full guide.

**Pattern:**
1. Define cell content as string constants (`r"""..."""`)
2. Use helpers: `md_cell(source)`, `form_cell(source)`, `build_notebook(cells)`
3. Assemble cells in presentation order as a list
4. Write as JSON via `json.dump()` to `.ipynb`

**Shared cell groups** (copy from `create_prototype_demo.py`):
- Package installation (provider-specific pip install with output suppressed)
- Setup + FHIR connection + provider adapter (3 functions)
- Tool definitions (FHIR query functions + provider-neutral tool schemas)
- Validation cell (quick query to confirm data access)

Activity-specific cells come after the shared groups and vary entirely by use
case. The framework does not constrain what comes after setup.

**Corresponding smoke test:** Extract cells, strip `#@param`, run via `exec()`
with mocked inputs, per-cell timeouts (180s for agent cells, 60s for others),
skip LLM-dependent cells. Reports PASS/FAIL per cell.

## Clinical Agent Pipeline

Four domain-independent agents support the end-to-end workflow. Each has a
permanent identity (`AGENT.md`) plus per-project context (`project-brief.md`).
See [TECHNICAL.md](TECHNICAL.md#clinical-agent-pipeline) for the full
architecture, decision boundaries, and communication protocol.

### Agent 1: Clinical Scenario Designer

**Trigger:** `/scenario-design`
**Identity:** `.claude/agents/clinical-scenario-designer/AGENT.md`

Designs clinical scenarios from three perspectives: clinician (what evidence
matters), dataset architect (what queries are needed), teacher (is this
non-trivial). Has access to ICD-10, PubMed, and bioRxiv MCP tools.

**Decides:** Clinical question, categories, evidence types, difficulty.
**Does NOT decide:** Code, cell layout, data generation parameters.
**Produces:** `docs/scenarios/<name>.md`
**Escalates:** Data availability (to Synth Data), difficulty (to Edu Review).

### Agent 2: Synthetic Data Architect

**Trigger:** `/synth-data`
**Identity:** `.claude/agents/synthetic-data-architect/AGENT.md`

Translates scenario designs into phenotype configs: anchors, distributions,
categorical probabilities, coupling constraints. Runs test batches and
validates clinical plausibility.

**Decides:** Phenotype parameters, cohort composition, coupling constraints.
**Does NOT decide:** Clinical question, categories, pedagogy.
**Produces:** Phenotype JSON configs, cohort plans.
**Escalates:** Missing generator variables (produces spec), ambiguous anchors.

### Agent 3: Clinical Education Reviewer

**Trigger:** `/edu-review`
**Identity:** `.claude/agents/clinical-education-reviewer/AGENT.md`

Evaluates whether a notebook delivers on its learning objectives. Applies
the "Bored or Baffled" framework. Checks for: passive observation, trivially
solvable tasks, missing feedback, false agency, opaque AI.

**Decides:** Learning quality, activity design, difficulty calibration.
**Does NOT decide:** Clinical thresholds, code, technical correctness.
**Produces:** Structured review with severity ratings.
**Escalates:** Clinical accuracy (to Scenario Designer), tech UX (to Impl Reviewer).

### Agent 4: Notebook Implementation Reviewer

**Trigger:** `/nb-preflight`
**Identity:** `.claude/agents/notebook-implementation-reviewer/AGENT.md`

Checks 10 categories: form/widget syntax, string escaping, cell dependencies,
Run All compatibility, package installation, secrets handling, data query
patterns, output/display, code visibility, generator consistency. Also checks
clinical coherence against the scenario design document.

**Decides:** Technical correctness, Colab compatibility, scenario coherence.
**Does NOT decide:** Pedagogy, scenario design, data generation.
**Run BEFORE Colab verification** — no point verifying rendering of broken code.

### Inter-Agent Communication

- **Scenario design documents** (`docs/scenarios/*.md`) are the primary shared
  artifact. The Scenario Designer produces them; all others consume them.
- **Query files** (`agent-history/comms/queries/`) for decisions that cross
  agent boundaries.
- **Response files** (`agent-history/comms/responses/`) for answered queries.
- **Session files** (`agent-history/sessions/`) for cross-conversation context.
- **Decision boundary rule:** Agents flag decisions outside their domain rather
  than making them.

## Conventions

- **Notebooks are generated, not hand-edited.** Always edit the generator script
  and re-run. Never edit `.ipynb` files directly.
- **Self-contained Colab notebooks** — Generated notebooks inline all code as
  string constants. No `src/` imports in generated notebooks.
- **FHIR server** — Configurable via `.env`. Default: SBU LinuxForHealth at
  `https://lfh-fhir.eastus2.cloudapp.azure.com:9443/fhir-server/api/v4`,
  Basic Auth (`fhiruser`/`BmI512@ccess`), self-signed cert. 1,027 synthetic
  patients across 6 phenotypes.
- **LLM** — API-agnostic provider support. Students choose Anthropic
  (`claude-sonnet-4-20250514`) or OpenAI (`gpt-4.1-mini`) via a dropdown in
  Step 1. A thin 3-function adapter (`_llm_create`, `_llm_serialize_assistant`,
  `_llm_format_tool_results`) normalizes tool calling differences. Tool schemas
  use provider-neutral `"parameters"` key, converted at call time. Both providers
  verified end-to-end on Vertex AI (2026-03-28).
- **Clinical thresholds** — Scenario-specific. For diabetes: HbA1c >7.5% =
  suboptimal, >9.0% = poor. See each scenario's design doc for authoritative
  thresholds.
- **FHIR query banners** — Every query result displays the FHIR URL. Students
  are learning FHIR, not just doing clinical exercises.
- **"You Are the Agent" pedagogy** — Human → Hybrid → LLM progression. Menu-driven
  interaction in human mode (no code writing by students). This is the first use
  case, not the framework's only pattern.

## Notebook Debugging Strategy

When debugging notebooks end-to-end, do NOT use `nbconvert --execute` (too slow,
no incremental feedback, hangs on `input()` calls). Instead:

1. Create a temporary harness script (e.g., `debug_session.py`) that:
   - Extracts code cells from the notebook in order
   - Runs each cell in a shared namespace via `exec()`
   - Reports PASS/FAIL with timing after each cell
   - Caps agent `max_steps` at 5 (enough to verify the loop works)
   - Mocks `input()` calls with test values
   - Uses per-cell timeouts (180s for agent cells, 60s for others)
   - Fails fast if setup/connectivity cells fail
2. Run the harness and report results per cell group
3. Fix errors in the generator script (not the notebook directly), regenerate, re-run
4. Clean up the harness script when done

## Verification — Hard Rules

**Notebooks must be verified running against the live FHIR server.** No mocks,
no "it should work." This project produces educational materials where the UI
and user experience are the product.

**Use API calls to verify the notebook works. If you do not have the API key,
STOP and ask the user. Store this key in a `.env` file in the root of the
project.**

### Two-Stage Process

1. **Automated (Claude's job):** Programmatic cell execution against the live
   FHIR server via Vertex AI Workbench (SSH tunnel + Jupyter MCP). Evaluates
   technical correctness, FHIR connectivity, cell execution, and output
   formatting. This is the iteration loop — fix issues in the generator,
   regenerate, re-verify until clean. Legacy alternative: Playwright-based Colab
   screenshots via `scripts/colab-tools/colab_screenshot.py`.

2. **Manual (Joel's job):** Once automated testing passes, Joel reviews in Colab
   for the student experience — pedagogy flow, clarity, visual polish, widget
   rendering. This is the sign-off, not the debugging loop.

### What Counts as Verified

1. **Local harness passes** (see Notebook Debugging Strategy above) — necessary
   but NOT sufficient.
2. **Automated execution against live FHIR data** shows all cells succeed with
   correct output. Claude reviews these results.
3. **Change-specific checklist** — every user-visible change is confirmed in at
   least one verification output (see below).
4. **Joel's manual review** confirms the student experience is correct. This is
   the final deliverable.

### What Does NOT Count

- `nbconvert --execute` passing locally
- "The code looks correct" or "this should work"
- Running cells in a local Jupyter instance (Colab has different behavior)
- Testing against a mock or local FHIR server
- Verifying only the generator script without running the generated notebook

### Notebook Change Sequence

**Any time a notebook is created or modified, it MUST be tested against the live
FHIR server before the change is considered complete.** This is not optional and
not deferrable. The sequence is:

1. Regenerate the notebook from the generator script
2. Run local validation (`nb_validate.py` + smoke test)
3. Execute all cells via Vertex AI (or upload to Colab for legacy path)
4. Review output for errors, rendering issues, and correct behavior
5. Fix → regenerate → re-verify until clean

Skipping verification because "the code looks correct" or "it passed locally"
is never acceptable.

### Change-Specific Verification

After verification, Claude MUST confirm each specific change from the
implementation plan/task is present in the output.

**Process:**
1. Before reviewing results, write out a **verification checklist** — every
   user-visible change that was made (new UI elements, removed columns, updated
   text, new dropdowns, new output sections, etc.)
2. Review verification output and check off items that are confirmed
3. If ANY item is not confirmed:
   - Do NOT declare verification complete
   - Do NOT say "cannot verify from these results" and move on
   - **For screenshot-based verification:** Re-run with `--num-sections`
     increased (e.g., 10, 15, 20) until the missing item is captured
   - **Only if an item physically cannot be captured** (e.g., requires
     interactive input that Run All does not provide): explicitly tell the user
     which items need manual verification and why
4. Only declare verification complete when every checklist item is either
   confirmed or explicitly flagged with a concrete reason why automated capture
   is impossible

**The anti-pattern this prevents:** Running verification, eyeballing results,
and saying "looks clean" without checking whether every change is actually
visible. If you made 8 changes and can only confirm 5, verification is NOT
complete.

### When to Stop and Ask

If you cannot verify (e.g., Vertex AI down, auth issues, FHIR server
unreachable), **stop and tell the user**. Do not substitute a lesser form of
verification and call it done. The user will decide how to proceed.

**Resource unavailability rule:** When any required resource is unavailable
(FHIR server, API key, Vertex AI, Colab auth), never mock it, never fall back
to a substitute, never continue with degraded resources. Stop and ask. Degraded
resources produce misleading results, and a workaround that silently changes
test conditions is worse than stopping. This applies with extra force during
testing and validation.

## Google Vertex AI Workbench

Vertex AI Workbench replaces Playwright-based Colab automation for notebook
verification. An SSH tunnel connects `localhost:8888` to the Jupyter server on
a `e2-standard-4` VM in `us-east4-a`, and the `mcp-jupyter` MCP server provides
programmatic cell execution with structured output capture. A PreToolUse hook
auto-starts the instance and tunnel before any `mcp__jupyter__*` call, and a Stop
hook shuts it down when Claude Code exits. The full setup procedure, failure modes,
and recovery steps are documented in the skill at `~/.claude/skills/colab-mcp/SKILL.md`.
Trigger with: "connect to Colab", "set up Vertex AI", or `/colab-mcp`.

## Colab Notebook Tools Skill (Legacy Playwright)

A local Claude Code skill at `.claude/skills/colab-notebook-tools/` covers the
full notebook lifecycle: create, edit, validate, execute in Colab, visually verify.
**Superseded by Vertex AI Workbench** for automated verification, but still
available for visual checks and screenshot-based review.

**Skills available:** `/nb-auth`, `/nb-validate`, `/nb-verify`, `/nb-review`, `/nb-ship`
**Scripts:** `scripts/colab-tools/` (auth_setup.py, colab_screenshot.py, nb_validate.py, nb_exec_harness.py)
**Config at `~/.colab-notebook-tools/`:**
- `auth.json` — Playwright storageState (Google session cookies)
- `browser_data/` — Persistent Chromium profile for `auth_setup.py`

**Auth approach:** `auth_setup.py` uses `launch_persistent_context` with anti-detection
args (`--disable-blink-features=AutomationControlled` + `ignore_default_args=["--enable-automation"]`)
to bypass Google's automation blocking. After sign-in, cookies are exported via
`storageState` for use by `colab_screenshot.py`.

**Scroll handling:** Colab uses `<colab-scroller id="notebook-main">` as its scroll
container. The screenshot script detects this and scrolls it directly (not `window.scrollTo`).

**Dialog handling:** The screenshot script automatically handles two Colab dialogs
that block execution:
- **"Notebook does not have secret access"** — Auto-clicks "Grant access" so
  notebooks can use Colab Secrets (e.g., `ANTHROPIC_API_KEY`). The secret must
  already exist in the user's Colab account. Use `--no-grant-secrets` to prevent
  auto-granting. Colab uses shadow DOM for its dialogs, so the handler uses
  JavaScript to recursively search shadow roots for buttons.
- **"Too many sessions"** — Clicks "Manage sessions", terminates old sessions,
  and retries the runtime connection. If the dialog reappears during Run All
  execution, the script automatically reconnects and re-triggers Run All (with
  timer reset). Handles multiple consecutive session dialogs. Common after
  repeated automated test runs.

**Cached outputs warning:** After `colab_screenshot.py` runs a notebook, Colab
auto-saves cell outputs to the Drive file. If someone later opens this notebook
and runs cells individually, they'll see stale cached outputs that may look like
a cell has already completed when it's still running. Always upload a fresh
notebook (regenerated from the generator, with `"outputs": []`) before sharing.

The skill is symlinked to `~/.claude/skills/colab-notebook-tools` for global
availability. **Future plan:** extract into a standalone distributable plugin.
